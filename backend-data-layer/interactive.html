Database Choice

"Where do the rows live?" — SQL vs NoSQL, schemas, and why indexes matter.

SQL

Relational — Rows, Columns, Indexes (Postgres)

▼
A relational database stores rows in fixed-shape tables. Schema is enforced at write time: every row of students has the same columns, with the same types. SQL is the common query language. Postgres is the default pick for almost any new app — strong consistency, rich types (JSON, arrays, geo), and a great ecosystem.
Analogy: A spreadsheet on steroids click

Like a spreadsheet — every row has the same columns, types are enforced. Unlike a spreadsheet — billions of rows, transactions, indexes, and many users editing at once without stepping on each other.

The trade-off: faster reads, slower writes click
  • An index is a second copy of the data, sorted. Reads use the sorted copy to jump straight to matching rows.
  • Every INSERT, UPDATE, and DELETE has to keep that copy in sync. One extra B-tree write per index, per row touched.
  • Concrete cost: ~30–80% slower writes per index. With 5 indexes a write-heavy table can be 4–5× slower than the same table with none.
  • Storage cost too: indexes take disk + memory. A 100GB table with five indexes can use 200–300GB total.
  • Rule of thumb: index columns you filter or join on in hot paths. Skip columns that change a lot, have low cardinality (e.g. a 3-value status), or are queried only by background jobs.
  • Read-heavy table? Index aggressively. Write-heavy table? Index sparingly — the savings on reads stop paying for the cost on writes.
What if you skip indexes? click
  • 10 rows: nobody cares.
  • 10 million rows: a missing index turns a 2 ms query into a 2 second query, your DB CPU spikes, and connections back up.
  • Production incidents are usually missing or wrong indexes — not bad code.
NoSQL

Document Store — Flexible Schema (MongoDB)

▼
A document store keeps records as JSON-like documents. The schema isn't enforced at write time — two documents in the same collection can look very different. Queries are nested filters, not joins. Good when shape varies a lot, when you write many self-contained records, or when you intentionally denormalize for read speed.

When NoSQL pays off click
  • Variable shape: CMS content, IoT events, user-defined fields — fewer migrations.
  • Read-heavy with denormalization: embed sub-documents to avoid joins.
  • Horizontal scale: sharding is built in.
When NoSQL hurts you click
  • Relations: "user has many orders, each with many items" — joins are clunky in Mongo. Postgres makes you smile.
  • Strict consistency: banks, billing, inventory. SQL transactions are the right tool.
  • Schema drift: "no schema" really means "schema in your application code". When that drifts, you're debugging optional fields forever.

ORM / Query Layer

"How does my code talk to the database?" — and the N+1 query trap.

PYTHON

SQLAlchemy — and the N+1 Trap

▼
An ORM (Object-Relational Mapper) maps your Python classes to DB tables. SQLAlchemy is the standard. It's amazing — until you hit N+1 queries: code that looks like one operation actually fires N+1 SQL statements. The fix is joinedload (or selectinload): tell the ORM to fetch the related rows in the same trip.

Why N+1 is the most common backend bug click
  • The code reads like a single line: for s in students: print(s.courses).
  • Behind the scenes the ORM lazy-loads s.courses for each student — that's N extra queries.
  • Fine with 5 students. With 5,000, that's 5,001 round trips. Page takes 30 seconds.
  • Fix: select(Student).options(joinedload(Student.courses)).
How to spot N+1 in production click
  • Turn on SQL logging in dev (echo=True). Read the log of a single page load.
  • If you see the same SELECT ... WHERE ... = ? repeated dozens of times, you have N+1.
  • APMs (Datadog, NewRelic, Sentry) flag this directly.
JS / TS

Prisma — Same Trap, Same Fix

▼
In the JS/TS world, Prisma is the most popular ORM. The N+1 pattern is the same — you call findMany(), then access a relation per row, and Prisma quietly fires N follow-up queries. The fix in Prisma is include: declare the relation up front and Prisma fetches everything in batched queries.

Prisma's two-query trick click
  • With include, Prisma fires two queries: one for students, one for the courses of those students (using WHERE student_id IN (...)).
  • It then assembles the JSON in JS. Two queries instead of N+1, no risky cartesian JOIN.
  • This is similar to SQLAlchemy's selectinload.

Migrations & Schema Evolution

"How does the schema change without losing data?" — versioned, reversible, deployed.

Edit model➔ Generate migration➔ Review SQL➔ Apply (upgrade)➔ Roll back if needed
PYTHON

Alembic — Time-travel for your Postgres Schema

▼
Alembic is SQLAlchemy's migration tool. Each schema change becomes a small Python file (a "revision") with upgrade() and downgrade() functions. The DB stores which revision is currently applied (alembic_version table). You can move forward or backward step by step.

Console
Click a button — current state shown above.
Why migrations are checked into git click
  • Migrations are code. They are reviewed in PRs like any other change.
  • CI applies migrations to a fresh DB to verify they actually run.
  • Every environment (dev, staging, prod) ends up at the same revision the same way.
Things migrations cannot save you from click
  • NOT NULL on a populated table without a default — fails on existing rows.
  • Renaming a column while old code is still reading the old name — old pods crash.
  • Long-running ALTERs on huge tables — locks everything. Use safe-migration tools (pg_repack, gh-ost) or the expand-then-contract pattern.
JS / TS

Prisma Migrate — Schema-driven Diff

▼
Prisma takes a different angle: your schema lives in schema.prisma. You edit that file, then run prisma migrate dev --name "add_email". Prisma diffs your edited schema against the DB and generates a SQL migration for you — and applies it.

Schema-first vs migration-first click
  • Alembic (migration-first): you write the migration; it's the source of truth.
  • Prisma (schema-first): you write the schema; the migration is generated by diff.
  • Both work. Schema-first is faster on small teams; migration-first gives you finer control on big teams with painful production tables.

Transactions, Connections & Caching

"How does the data layer behave under load?" — three runtime concerns that ship with every backend.

Request➔ Get connection (pool)➔ Cache check➔ BEGIN➔ DB write➔ COMMIT or ROLLBACK
ACID

Transactions — Bank Transfer Demo

▼
A transaction wraps multiple operations in an "all-or-nothing" envelope. Either every step commits or none of them do. The classic example: transfer $100 from A to B. Without a transaction, a crash between the debit and the credit means the money disappears. With a transaction, the DB rolls back to the state before BEGIN — as if nothing happened.

ACID in one line each click
  • A — Atomicity: all steps commit, or none do.
  • C — Consistency: the DB is left in a valid state (constraints honored).
  • I — Isolation: concurrent transactions don't see each other's half-done work.
  • D — Durability: once COMMIT returns, the change survives a crash.
Where developers forget transactions click
  • Multi-row writes in the same logical operation (create order + decrement stock).
  • External calls inside transactions — long HTTP calls hold a DB connection. Bad. Pull the call out, or use the outbox pattern.
  • "It looked atomic in code" — Python's session.add() followed by session.commit() is one transaction; two separate commit() calls are two.
RUNTIME

Connection Pooling — Why It's Not Optional

▼
Opening a fresh DB connection per request is expensive (TCP handshake + TLS + auth). A connection pool keeps a small set of long-lived connections and hands them out. When the pool is full, new requests wait in a queue.

Pool state
Send some requests and watch the pool.
Sizing the pool click
  • Postgres default max_connections is 100. With 10 app instances × pool_size 20 = 200 → connection refused.
  • Rule of thumb: pool_size ≈ cores × 2 per instance, leave room for migrations & admin tools.
  • Use PgBouncer in front of Postgres for high-concurrency setups — it multiplexes connections.
What if you forget to release a connection? click
  • Pool fills up, new requests queue, then time out.
  • Common cause: an exception inside a with session.begin() that wasn't handled — the framework should release, but only if you used the framework's helper.
  • Symptom in production: 502s under modest load with the DB barely doing any work. The bottleneck is the pool, not the DB.
RUNTIME

Caching — Read-through with Redis

▼
A cache (typically Redis) sits in front of the DB. The "read-through" pattern: check cache → on miss, query DB → store result in cache → return. The next read is a cheap memory hit. Each entry has a TTL so it eventually refreshes.

Cache invalidation — the hard part click
  • "There are two hard things in computer science: cache invalidation, naming, and off-by-one errors."
  • TTL is the simplest answer — entries expire on their own. Stale data is bounded.
  • Write-through: on every write, also update the cache (or delete it). More work, fresher data.
  • Patterns to avoid: caching things that change often, caching per-user data with no key for the user, caching DB writes (you'll get phantom rows).
When a cache becomes a liability click
  • Stampede: popular key expires, 10,000 concurrent requests all miss at once and pound the DB. Use a single-flight lock or randomize TTL.
  • Stale reads after a write: user updates profile, sees the old version because the cache wasn't busted.
  • If the data is small and cheap to fetch from Postgres, you might not need a cache at all. Measure first.

Analogy: A restaurant kitchen click

  • ORM = the line cook reading order tickets and grabbing ingredients.
  • Migration = remodeling the kitchen between services without losing the food in the fridge.
  • Transaction = "fire the burger and the fries together, or refire both" — all on one ticket.
  • Connection pool = the fixed number of stoves. Tickets wait if all are in use.
  • Cache = the warming tray. Fast to grab, but you can't keep food there forever.
One request, every layer click
POST /students {name:"Ana", year:3}
  → API handler
  → check Redis cache for "student_count"   (cache: optional, runtime)
  → acquire pooled DB connection            (pool: runtime)
  → BEGIN                                   (txn: runtime)
  → INSERT INTO students (name, year) ...   (ORM: SQLAlchemy / Prisma)
  → INSERT INTO audit_log ...
  → COMMIT
  → release connection
  → invalidate "student_count" cache
  → return 201 with the new row

Every concept in this playground shows up in those ten lines. That's the whole shape of a backend data layer.

If you only learn one thing per layer click
  • DB: index where you query.
  • ORM: watch for N+1; eager-load relations you'll touch.
  • Migrations: always provide a downgrade; never break the schema for old code that's still running.
  • Transactions: wrap related writes; never call slow external APIs inside one.
  • Pool: always release; size it for the DB, not for hope.
  • Cache: set a TTL; assume invalidation will be wrong sometimes.
