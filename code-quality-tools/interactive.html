Code Quality Tools Playground

Four tools, four questions. Touch each one. Watch them fire on a commit. — Python & JS/TS.

1

Formatter

"Does this look consistent?" — rewrites style only, never logic.

Messy source➔ Formatter➔ Spacing fixed➔ Quotes normalized➔ Lines wrapped➔ Same code, clean look
PYTHON

Black — Format Messy Python In One Click

▼
Black is opinionated by design: almost no config. You give it ugly Python, you get back the canonical layout — 4-space indent, double quotes, blank lines around def/class, lines wrapped at the limit. It only changes how the code looks, never what it does.
Analogy: A laundry-fold robot click

You hand it a pile of clothes (messy code). It folds them all the same way (consistent style). It does not tell you the shirt is on backwards (logic bugs) — it just folds.

Why pick Black over alternatives? click
  • Zero-config: you accept Black's style and stop arguing about tabs vs spaces.
  • Idempotent: running Black twice is the same as running it once.
  • Wide adoption: works the same way in every project, every IDE.

What Black does NOT catch click
  • Bugs: def add(a, b): return a - b formats fine. The minus is none of Black's business.
  • Unused imports: Black leaves import os alone even if you never use it. (That's the linter's job.)
  • Wrong types: add("1", "2") formats cleanly even though strings into int params will explode. (That's the type checker's job.)
JS / TS

Prettier — The JS/TS Equivalent of Black

▼
Prettier is the de facto JS/TS formatter. Same philosophy as Black: opinionated, almost no knobs. Handles JS, TS, JSX, JSON, CSS, Markdown, YAML — all in one tool. Pairs with ESLint via eslint-config-prettier so the two never argue.
Black ↔ Prettier — same job, different ecosystem click
  • Same goal: kill the style debate.
  • Same trick: no config, just run it.
  • Different scope: Prettier covers more file types because the JS world has many.

Common Prettier-vs-ESLint confusion click
  • Prettier formats. ESLint lints. Don't make ESLint enforce semicolons or quote style — that fights Prettier.
  • Install eslint-config-prettier and put it last in your ESLint config. It disables every ESLint rule that overlaps with Prettier.
  • Result: Prettier owns layout, ESLint owns code-quality rules. No conflicts.

Linter

"Is this suspicious or wrong?" — a tireless code reviewer that flags bad patterns.

Source code➔ Static analysis➔ Pattern rules➔ Warnings➔ Auto-fix or block
PYTHON

Ruff — Spot Suspicious Python Code

▼
Ruff is a Rust-based Python linter that bundles dozens of rule sets (pyflakes, pycodestyle, isort, pyupgrade, bugbear, ...) into one binary. It's 10–100× faster than the older Python linters. It can also auto-fix most of what it finds.
Analogy: A code reviewer that never sleeps click

It doesn't run your code. It just reads it and goes: "you imported os but never used it", "this variable is dead", "this comparison should be is None". You decide whether to fix or ignore.

Why one tool replaced five click
  • Before Ruff: Flake8 + isort + pyupgrade + pylint + bugbear — 5 tools, 5 configs, 5 install steps.
  • With Ruff: one binary, one block in pyproject.toml, faster than any of the originals.
  • You pick rule families with select = ["E","F","I","B","UP"] — that's pycodestyle, pyflakes, isort, bugbear, pyupgrade in one line.
What the linter still cannot catch click
  • Wrong logic: def divide(a, b): return a + b looks fine to Ruff.
  • Wrong types: Ruff doesn't read your annotations as types. (MyPy does.)
  • Cross-file behavior: A linter sees one file's patterns. It can't simulate your whole program.
JS / TS

ESLint — Spot Suspicious JS/TS Code

▼
ESLint is the de facto JS/TS linter. With typescript-eslint it understands TypeScript types and adds dozens of TS-specific rules. Modern flat config (eslint.config.js) keeps the setup small.

Why pair ESLint with Prettier click
  • Make ESLint enforce code-quality rules (no any, no console.log, hook rules, ...).
  • Let Prettier own layout (quotes, semis, indent).
  • Add eslint-config-prettier last so they don't fight.
Common ESLint mistakes click
  • Disabling rules with // eslint-disable instead of fixing them. Six months later, the file is a graveyard of disabled lines.
  • Using ESLint as a type checker. ESLint can flag type smells; tsc --noEmit is the actual type checker.
  • Letting ESLint and Prettier fight. Always add eslint-config-prettier last in your config.

Type Checker

"Are types used correctly?" — proves shape without running the code.

Annotated source➔ Static analysis➔ Type inference➔ Argument check➔ Type errors
PYTHON

MyPy — Catch Type Mismatches Before You Run

▼
Python is dynamically typed at runtime — but with type hints (def f(x: int) -> str:), MyPy can statically prove that values flow through your code in compatible types. It only checks what you've annotated — no annotations means no signal.
Analogy: A passport check at the airport click

Each function parameter has a "country" (a type). The type checker is the gate agent: "you said you're flying to int-land, but your passport says str." No flight runs — the mismatch is caught at the gate.

What MyPy still cannot do click
  • Logic bugs: def add(a:int,b:int)->int: return a-b is type-correct. Tests catch this; types don't.
  • Untyped code: if you don't annotate, MyPy has no signal. Strict mode fails on missing annotations on purpose.
  • Highly dynamic Python: getattr, **kwargs, monkey-patching — types can only go so far.
JS / TS

TypeScript — tsc --noEmit as a Pure Type Checker

▼
TypeScript is two things: a language and a type checker. With tsc --noEmit we run the compiler in pure-check mode — no output files, just type errors. "strict": true in tsconfig.json is the single most important setting: it enables strictNullChecks, noImplicitAny, and friends.

Why any is the silent killer click
  • any tells the type checker "trust me, don't look". Bugs slip past silently.
  • Same for // @ts-ignore — you've turned the alarm off, not fixed the wiring.
  • Use unknown when you don't know the type yet. It forces a check before use.

Git Hooks

"Should this code even be allowed to commit?" — automation that wires the other three together.

git commit➔ Formatter➔ Linter➔ Type checker➔ Pass → commit / Fail → blocked
PYTHON

pre-commit — One YAML Wires Black + Ruff + MyPy

▼
Raw .git/hooks/ are per-clone and not version-controlled. The pre-commit framework solves that: hook config lives in a tracked .pre-commit-config.yaml, and pre-commit install drops the actual scripts into .git/hooks/ for every team member.

Why "files were modified by this hook" is a feature click
  • If Black reformats your file, pre-commit rejects the commit. That's intentional.
  • The reason: your staged content no longer matches the files on disk. Re-stage with git add and commit again.
  • This guarantees: the code that lands in the repo is exactly what passed all checks.
--no-verify exists, but don't normalize it click
  • Anyone can bypass hooks with git commit --no-verify. That's by design — emergencies happen.
  • If a hook is wrong, fix the hook. Don't teach your team that bypassing is normal.
  • CI is the real backstop: even if someone --no-verify's, CI runs the same checks on the PR.
JS / TS

Husky + lint-staged — Two Tools, One Pipeline

▼
In the JS/TS world, the same job is split between two tools:
  • Husky — manages .git/hooks/ from a tracked .husky/ directory.
  • lint-staged — runs commands only on staged files so commits stay fast.

Why tsc runs on the whole project, not staged files click
  • Type checking needs the whole module graph: a change in a.ts can break b.ts that imports from it.
  • If lint-staged ran tsc on just a.ts, you'd miss the breakage in b.ts.
  • So: Prettier + ESLint on staged files (fast). tsc --noEmit on the whole project (correct).

The Big Picture

Why each tool is a different question — and why none replaces the others.

REVIEW

Four Tools, Four Questions

▼
Each tool answers a question the others can't. That's why you need all four — they don't overlap. The git hook is the glue: it makes the other three run on every commit so nothing slips by.
Formatter
"Does this look consistent?"
  • Black (Python)
  • Prettier (JS/TS)
  • Touches layout only
  • Auto-rewrites
Linter
"Is this suspicious or wrong?"
  • Ruff (Python)
  • ESLint (JS/TS)
  • Pattern-based warnings
  • Often auto-fixable
Type Checker
"Are types used correctly?"
  • MyPy (Python)
  • TypeScript (JS/TS)
  • Static type analysis
  • Cross-file
Git Hooks
"Should this commit?"
  • pre-commit (Python)
  • Husky + lint-staged (JS/TS)
  • Runs the other three
  • Blocks bad commits
Analogy: Building a house click
  • Formatter = paint & trim. Makes the house look uniform.
  • Linter = the inspector who walks through pointing out exposed wires.
  • Type checker = the structural engineer. "This beam can't carry that load."
  • Git hooks = the city permit office. You don't get a certificate of occupancy until the other three sign off.
Same code, four different views click

Look at this snippet:

import   os
def divide(a: int, b: int) -> int:
    return a + b

result = divide("10", "2")
  • Formatter sees: extra spaces. Fixable: yes.
  • Linter sees: os imported but not used. Fixable: yes (remove it).
  • Type checker sees: "10" and "2" are strings, not ints. Fixable: yes (cast or fix the call).
  • None of them see the real bug: the function says "divide" but adds. Only tests catch that.
What if you only use one of the four? click
  • Only formatter: code is pretty but full of bugs and dead imports.
  • Only linter: bugs caught, but the team still argues about quotes.
  • Only type checker: shape is correct, but unused code rots and style drifts.
  • Only git hooks: nothing actually runs — the hook is a wrapper around the other three.
